# Регламент команды — где работать и как сдавать

Справочник скилла `su10-design-system`. Основной файл отвечает на вопрос «как собрать экран»,
`handoff.md` — «как разложить экраны для разработки», этот — **где лежит работа на каждом этапе
и как готовая фича попадает в чистовой файл**. Обязателен для всех, кто генерирует макеты и
работает в Figma.

**Когда открывать:** начинаешь новую фичу; финальный дизайн апрувнут и его надо перенести;
просят «перенеси в чистовой», «положи в проект студента», «создай файл раздела», «куда это
класть»; нашёл в работе правило, которого нет в скилле.

---

## 1. Путь фичи

```
1. Черновик          → проект JUZ40 Workspace / личный файл участника команды («Aldik», «Oraz» …)
2. Генерация         → только этим скиллом
3. Новое знание      → в скилл на GitHub (доступ — у Nurla)
4. Апрув финала      → «подготовь к хэндоффу» — доска сценариев по handoff.md
5. Чистовой файл     → проект роли / файл «<Раздел> (<Роль>)» / страница «<Фича> [<Месяц> <Год>]»
6. Ready for dev     → вручную ставит тот, кто перенёс, только на готовые секции
```

## 2. Черновики — личный файл в JUZ40 Workspace

- У каждого участника команды в проекте **JUZ40 Workspace** свой файл, названный его именем.
- Фича живёт там всё время работы: варианты, итерации, правки по ревью.
- Чужие файлы не правят (железное правило 8: нужен чужой блок — клон к себе).
- Из личного файла в разработку не отдают: разработка получает только чистовой файл.

## 3. Генерация — только этим скиллом

Экраны, флоу, формы, оверлеи, таблицы — только по правилам основного файла: компоненты SU10,
переменные, текстовые стили, аудит перед сдачей. Ручная сборка в обход скилла запрещена.

- **Старый кит** (`JUZ40 UI-Kit`, `Juz40 Landing`) — при надобности можно брать готовые блоки
  из старых макетов. Сначала проверить SU10: есть там — брать из SU10.
- **Нет в SU10** — сразу сгенерировать вариант и оформить **компонентом в своём файле** по
  правилам системы, понятное имя (`StatTile`, `Chart / Line`, `EmptyState`), в макете — его
  инстансы. Написать Nurla со ссылкой: он перенесёт компонент в дску. Подробно — раздел
  «Чего в системе нет» в `SKILL.md`.
- Нельзя: брать блок со старого кита, когда такой есть в SU10; рисовать недостающее разовыми
  фреймами без компонента.

## 4. Новое знание — в скилл на GitHub

Нашёл правило, ловушку, баг компонента, новый ключ или устаревшую информацию — это идёт в
скилл, а не остаётся в одном макете.

1. **Доступ.** Коллаборатором в `nurlanartikbaev/su10-plagins` добавляет Nurla. Без
   выданного доступа не пушат, через чужой аккаунт — тоже.
2. **Правка** — в `SKILL.md` или нужный справочник в `references/`.
3. **Запись в `changelog.md`** — что и почему. Без записи правку не пушат.
4. **Пуш** делает хук `tools/su10-autopush.sh` (patch-версия, автор, коммит). Новый компонент
   или раздел — минорная версия, её поднимают руками до коммита.

## 5. Хэндофф и перенос в чистовой файл

### 5.1. Собрать к хэндоффу

После апрува финального дизайна — запрос «подготовь к хэндоффу» и сборка доски сценариев по
`handoff.md`: секция `<Раздел> — сценарии для разработки`, дорожки, пары тем, стрелки, чистка,
аудит, отчёт. Вручную доску не причёсывают.

### 5.2. Проект роли

Проект = **роль**, для которой сделана фича: Student, Parent, Curator, Admin и т. д. Фича
нескольких ролей раскладывается по проектам каждой роли, а не кладётся в один.

### 5.3. Файл раздела

Внутри проекта роли **один файл = один раздел кабинета**, в нём все задачи этого раздела.

Имя: `<Раздел> (<Роль>)` — `Главная (Student)`, `Календарь (Student)`, `Таск Трекер (Student)`,
`Аналитика ЕНТ (Admin)`.

Файла нет:
1. Сначала поискать в проекте роли — дубль раздела хуже, чем его отсутствие.
2. Создать файл в проекте роли с именем по шаблону.
3. Сразу заказать обложку (§5.6): её делает дизайнер.
4. **Написать команде** в общий канал, что заведён новый файл раздела, со ссылкой.

### 5.4. Страница фичи

Имя страницы: `<Фича> [<Месяц> <Год>]`, месяц — **когда апрувнули финальный дизайн**, не когда
начали. Пример: `Таск Трекер [Сентябрь 2026]`.

Порядок страниц:

```
Pages
├── Новая фича [Октябрь 2026]     ← новые — всегда самой верхней
├── Таск Трекер [Сентябрь 2026]   ← старые уходят вниз
├── ───────────                   ← разделитель
└── cover                         ← обложка всегда в самом низу
```

Старые страницы не удаляют и не переименовывают — это история раздела.

Через Plugin API страницу создают и ставят наверх так:
```js
const page = figma.createPage();
page.name = 'Таск Трекер [Сентябрь 2026]';
figma.root.insertChild(0, page);   // самой верхней
```
Скрипт работает в одном файле: экраны из личного файла в чистовой переносит человек
(копировать → вставить секцию целиком). Скилл может создать страницу в чистовом файле, если
дали его ссылку, и проверить результат после вставки.

### 5.5. Ready for development

`devStatus` через API не ставится. Статус **вручную ставит тот, кто перенёс фичу**, и
только на секции, готовые к разработке; секции в работе и в ожидании решения — без статуса.
Ссылку на секцию прикладывают к задаче.

### 5.6. Обложка

Обложку нового файла **делает дизайнер**. Если файл завёл не дизайнер, он сразу просит
дизайнера её сделать. Файл без обложки в проекте выглядит пустым тёмным квадратом.

- Страница `cover` внизу списка: название раздела крупно и подпись `JUZ40 <Роль>`.
- Фрейм обложки назначен превью файла (*Set as thumbnail*).
- **Обложку не рисуют заново — берут компонент `Cover`** (файл SU10 Design System, страница `cover`, ключ `59c45ae8ce5f89b3960e0a8295a8520a662eecc4`, 1720 × 960). Свойства: `Название` — название файла, `Папка` — проект роли (`JUZ40 Student`, `JUZ40 Parent` …). Блок текстов в автолейауте по центру, поэтому длинное и короткое название остаются по центру.
- Иерархия (решение владельца 20.10): **название файла крупнее всего → папка → логотип JUZ40 самым тихим**. Тёмная тема, все цвета — токены: фон `surface/1-layer`, название `text/primary`, папка `text/secondary`, логотип `icon/tertiary`, синее свечение снизу `surface/blue-static`. Куски продуктовых экранов, маскоты и яркие «конфетти» на обложку не ставят — владелец отверг.

## 6. Нельзя

- Отдавать в разработку из личного файла в Workspace.
- Заводить файл под каждую фичу: один раздел — один файл, фичи — страницами.
- Создавать дубль файла раздела или заводить файл молча, без сообщения команде.
- Оставлять новый файл без обложки.
- Ставить новую страницу фичи не первой сверху.
- Пушить в скилл без доступа или без записи в changelog.

## 7. Чек-лист перед передачей

| Пункт | |
|---|---|
| Фича сделана в личном файле в `JUZ40 Workspace` | §2 |
| Собрана этим скиллом, аудит пройден | §3 |
| Найденные правила внесены в скилл с записью в changelog | §4 |
| Доска сценариев собрана по `handoff.md`, отчёт прочитан | §5.1 |
| Проект роли и файл `<Раздел> (<Роль>)` найдены или созданы | §5.2–5.3 |
| Новый файл — обложка настроена, команда оповещена | §5.3, §5.6 |
| Страница `<Фича> [<Месяц> <Год>]` стоит самой верхней | §5.4 |
| Ready for development поставлен на готовые секции, ссылка в задаче | §5.5 |

## 8. Подсказка скиллу

Когда фичу просят перенести, а роль, раздел или месяц апрува не ясны — **спросить**, а не
угадывать. В отчёте после переноса напомнить про то, что делается руками: обложку нового
файла, сообщение команде и Ready for development.
